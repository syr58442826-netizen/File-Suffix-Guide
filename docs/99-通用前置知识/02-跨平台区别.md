# 02 - 跨平台区别

> Windows、Mac、Linux 三大系统看起来都是"电脑"，但在文件处理上有很多细节差异。了解这些差异，能帮你避免"为什么他能打开我不能"的尴尬。

---

## 一、三大操作系统文件系统概述

### 1.1 什么是文件系统？

文件系统就是操作系统管理硬盘上数据的方式。不同系统用的文件系统不一样，就像不同国家用不同的货币一样。

### 1.2 各系统的默认文件系统

| 操作系统 | 默认文件系统 | 特点 |
|----------|-------------|------|
| Windows | NTFS | 支持大文件、权限管理、加密 |
| Mac | APFS（新版）/ HFS+（旧版） | 对 SSD 优化、时间机器支持好 |
| Linux | ext4（最常见）、xfs、btrfs | 稳定、权限管理精细 |
| U盘/移动硬盘常用 | FAT32、exFAT | 跨平台兼容好，但各有限制 |

### 1.3 互相读取的兼容性

| | 读取 Windows (NTFS) | 读取 Mac (APFS) | 读取 Linux (ext4) |
|---|---------------------|-----------------|-------------------|
| **Windows** | ✅ 原生 | ❌ 需要第三方软件 | ❌ 需要第三方软件 |
| **Mac** | ✅ 能读，不能写（需开启写入） | ✅ 原生 | ❌ 需要第三方软件 |
| **Linux** | ✅ 基本都能读写 | ⚠️ 部分支持 | ✅ 原生 |

> **实用建议**：如果需要在 Windows 和 Mac 之间传文件，U盘格式化为 **exFAT** 是最佳选择，两边都能读写，也支持 4GB 以上的大文件。

## 二、换行符差异（CRLF vs LF）

### 2.1 什么是换行符？

换行符就是文本文件中表示"另起一行"的特殊字符。你在编辑器里按一下回车键，实际上就插入了一个换行符。

按理说换行符应该全宇宙统一，但历史原因导致了三大系统各不相同。

### 2.2 三大系统的换行符

| 系统 | 换行符表示 | 缩写 | 含义 | 字节数 |
|------|-----------|------|------|--------|
| Windows | `\r\n` | CRLF | 回车 + 换行 | 2 个字节 |
| Mac (OS X 以后) | `\n` | LF | 换行 | 1 个字节 |
| Linux / Unix | `\n` | LF | 换行 | 1 个字节 |
| 老版 Mac (OS 9 及以前) | `\r` | CR | 回车 | 1 个字节 |

> 注：`\r` 是 Carriage Return（回车，光标回到行首），`\n` 是 Line Feed（换行，光标下移一行）。这是打字机时代遗留下来的概念。

### 2.3 换行符不同会导致什么问题？

**问题一：显示异常**
- 在 Windows 上创建的 txt 文件，用某些 Linux 工具打开，每行末尾可能会多出一个 `^M` 符号
- 在 Linux 上创建的文本，用 Windows 记事本打开（老版本），可能所有文字挤在一行

**问题二：程序报错**
- 程序员最头疼的问题之一
- Shell 脚本如果是 CRLF 换行，在 Linux 上运行会报各种奇怪的错误
- 配置文件换行符不对可能导致程序读取失败

**问题三：Git 版本控制混乱**
- 团队协作时，Windows 和 Mac 混用，如果不设置好，每次打开文件 Git 都会显示"整文件被修改"，其实只是换行符变了

### 2.4 如何查看和转换换行符？

**查看换行符：**

| 平台 | 方法 |
|------|------|
| Windows | 用 Notepad++ 打开 → 右下角显示格式 |
| Mac | 终端输入 `file 文件名` |
| Linux | 终端输入 `file 文件名` |

**转换换行符：**

| 需求 | Windows 方法 | Mac/Linux 方法 |
|------|-------------|---------------|
| CRLF → LF | Notepad++ → 编辑 → 文档格式转换 → 转为 Unix | `sed -i 's/\r$//' 文件名` 或 `dos2unix 文件名` |
| LF → CRLF | Notepad++ → 编辑 → 文档格式转换 → 转为 Windows | `sed -i 's/$/\r/' 文件名` 或 `unix2dos 文件名` |

### 2.5 程序员的换行符最佳实践

1. **所有源代码统一用 LF**（这是行业标准）
2. **Windows 用户**设置 Git 的 `core.autocrlf = true`，自动在检出时转 CRLF、提交时转 LF
3. **Mac/Linux 用户**设置 Git 的 `core.autocrlf = input`
4. 项目根目录放一个 `.gitattributes` 文件，明确指定换行符规则

## 三、编码差异（GBK vs UTF-8）

### 3.1 什么是字符编码？

简单说，字符编码就是"文字在计算机里的存储方式"。同一个中文字符，在不同编码下存的二进制数据不一样，读的时候如果用错了编码，就会显示成**乱码**。

### 3.2 常见编码对比

| 编码 | 全称 | 特点 | 主要使用场景 |
|------|------|------|-------------|
| **UTF-8** | 8-bit Unicode Transformation Format | 可变长度、全球通用、兼容 ASCII | 互联网、Mac、Linux、现代软件 |
| **GBK** | 汉字内码扩展规范 | 专门为中文设计、2字节一个汉字 | Windows 简体中文版（老版本） |
| **GB2312** | 信息交换用汉字编码字符集 | GBK 的前身，字少一些 | 更老的系统 |
| **UTF-16** | 16-bit Unicode Transformation Format | 固定/可变长度 | Windows 内部使用、Java |
| **ASCII** | American Standard Code for Information Interchange | 只有英文字母和符号 | 基础英文 |

### 3.3 各系统默认编码

| 系统 | 默认编码 | 说明 |
|------|---------|------|
| Windows（简体中文） | **GBK** | 记事本默认保存为 GBK（新版已改为 UTF-8） |
| Mac | **UTF-8** | 全系统统一 UTF-8 |
| Linux | **UTF-8** | 绝大多数发行版默认 UTF-8 |

### 3.4 乱码的产生原因

**核心原因：存的时候用的编码，和读的时候用的编码不一样。**

举个例子：
- 你用 Windows 记事本写了"你好"，保存为 GBK 编码
- 把文件发给用 Mac 的朋友
- 朋友用默认 UTF-8 打开
- 结果：显示成一堆乱码（类似"ÄãºÃ"这种）

### 3.5 如何避免乱码？

**最佳方案：统一用 UTF-8**

1. **Windows 用户**：
   - 记事本保存时，编码选择 "UTF-8"（不要选默认的 ANSI/GBK）
   - 推荐使用 VS Code、Notepad++ 等编辑器，默认就是 UTF-8

2. **Mac/Linux 用户**：
   - 系统默认就是 UTF-8，一般不用管
   - 打开 Windows 传来的 GBK 文件时，手动选择 GBK 编码

3. **传文件前**：
   - 重要的文本文件，保存时选择 UTF-8 编码
   - 如果不确定对方用什么系统，优先选 UTF-8

### 3.6 乱码了怎么办？

**方法一：用编辑器切换编码**
- VS Code：右下角点击编码 → 通过编码重新打开 → 选择 GBK
- Notepad++：菜单栏 → 编码 → 选择合适的编码
- Mac 终端：`iconv -f GBK -t UTF-8 文件名 > 新文件名`

**方法二：用在线工具转换**
- 搜索"编码转换在线工具"
- 上传文件，选择源编码和目标编码

**方法三：用浏览器打开**
- 把 txt 文件拖进浏览器
- 右键 → 编码 → 选择正确的编码
- 然后复制内容出来

## 四、路径分隔符差异（\ vs /）

### 4.1 什么是路径分隔符？

路径就是文件在电脑上的"地址"，路径分隔符就是地址中分隔文件夹的符号。

### 4.2 各系统的路径分隔符

| 系统 | 分隔符 | 示例路径 |
|------|--------|---------|
| Windows | **反斜杠 `\`** | `C:\Users\小明\Documents\报告.docx` |
| Mac | **正斜杠 `/`** | `/Users/xiaoming/Documents/报告.docx` |
| Linux | **正斜杠 `/`** | `/home/xiaoming/documents/报告.docx` |

### 4.3 为什么会不一样？

这又是一个历史遗留问题：
- Unix 系统从一开始就用 `/` 作为路径分隔符
- 早期的 DOS（Windows 的前身）用 `/` 作为命令参数的前缀（比如 `dir /w`）
- 所以 DOS/Windows 只能用 `\` 来做路径分隔符
- 一直延续到今天

### 4.4 实际影响

**影响一：复制粘贴路径会出错**
- 从 Mac 复制的路径 `/Users/xxx/file.txt` 粘贴到 Windows 上不能直接用
- 反过来也是一样

**影响二：编程时容易踩坑**
- 代码里写死了 `C:\data\file.txt`，在 Linux 上运行就报错
- 专业的做法是用编程语言提供的路径拼接函数，自动适配系统

**影响三：相对路径写法**
- Windows 上：`..\上级目录\文件.txt`
- Mac/Linux 上：`../上级目录/file.txt`

### 4.5 小知识：Windows 其实也支持正斜杠

很多人不知道，Windows 的很多地方其实也能识别正斜杠 `/`：
- 在文件资源管理器的地址栏输入 `C:/Users` 也能打开
- 很多软件（特别是跨平台软件）内部用 `/` 也没问题
- 但 cmd 命令行里一般还是要用 `\`

## 五、可执行文件差异

### 5.1 各系统的可执行文件格式

| 系统 | 可执行文件后缀 | 格式名称 | 说明 |
|------|--------------|---------|------|
| Windows | `.exe` | PE (Portable Executable) | 最常见，双击就能运行 |
| Windows | `.msi` | Windows Installer | 安装包格式 |
| Mac | `.app`（其实是文件夹） | Bundle | 看起来是一个文件，实际是文件夹 |
| Mac | `.dmg` | 磁盘镜像 | 类似安装包，挂载后安装 |
| Mac | 无后缀（需加执行权限） | Mach-O | Unix 风格的可执行文件 |
| Linux | 无后缀（需加执行权限） | ELF | 大多数 Linux 可执行文件没有后缀 |
| Linux | `.deb`、`.rpm` | 软件包 | Debian/RedHat 系的安装包 |

### 5.2 为什么 .exe 在 Mac 上不能运行？

很多新手会问："为什么我下载的 .exe 文件，在 Mac 上双击没反应？"

答案很简单：**Windows 和 Mac 的可执行文件格式完全不一样，CPU 指令也不一样。**

就像你不能把 PlayStation 的游戏光盘插到 Xbox 上玩一样，不同系统的可执行文件是不兼容的。

### 5.3 脚本类文件的跨平台情况

脚本文件（`.py`、`.js`、`.sh` 等）的情况比较特殊：

| 脚本类型 | Windows | Mac | Linux | 说明 |
|----------|---------|-----|-------|------|
| `.py` (Python) | ✅ 需安装 Python | ✅ 需安装 Python | ✅ 一般自带 | 跨平台最好的脚本语言 |
| `.js` (Node.js) | ✅ 需安装 Node.js | ✅ 需安装 Node.js | ✅ 需安装 Node.js | 跨平台好 |
| `.bat` / `.cmd` | ✅ 原生支持 | ❌ 不支持 | ❌ 不支持 | Windows 专属批处理 |
| `.sh` (Shell) | ⚠️ 需 Git Bash/WSL | ✅ 原生支持 | ✅ 原生支持 | Linux/Mac 专属脚本 |
| `.ps1` (PowerShell) | ✅ 原生支持 | ✅ 可安装 PowerShell | ✅ 可安装 PowerShell | 跨平台版本已发布 |

### 5.4 跨平台运行的解决方案

| 方案 | 说明 | 适合场景 |
|------|------|---------|
| 虚拟机 | 在 Mac 上装个 Windows 虚拟机 | 偶尔需要用 Windows 软件 |
| 双系统 | 电脑上同时装两个系统 | 经常需要切换 |
| 兼容层 | 比如 Wine（Linux 运行 Windows 程序） | 技术用户，特定软件 |
| 找替代软件 | 找同功能的 Mac/Linux 版本 | 大多数办公软件都有替代 |
| 云服务 | 用云端的 Windows 主机 | 企业级需求 |

## 六、其他跨平台差异

### 6.1 文件名大小写敏感性

| 系统 | 大小写敏感？ | 说明 |
|------|-------------|------|
| Windows | ❌ 不敏感 | `File.txt` 和 `file.txt` 是同一个文件 |
| Mac | ❌ 默认不敏感 | 可以格式化为敏感模式，但默认不敏感 |
| Linux | ✅ 敏感 | `File.txt` 和 `file.txt` 是两个不同的文件 |

**常见坑**：
- 开发者在 Windows 上写的代码，引用了 `Image.png`，但实际文件名是 `image.png`
- Windows 上能跑，部署到 Linux 服务器就报错找不到文件

### 6.2 文件名禁止字符

| 系统 | 禁止在文件名中使用的字符 |
|------|------------------------|
| Windows | `\ / : * ? " < > \|` （共9个） |
| Mac | `:` （ Finder 中），底层和 Linux 一样 |
| Linux | `/` 和 `\0`（空字符） |

**实际影响**：
- 在 Mac 上创建了名为 `2024:报告.docx` 的文件，复制到 Windows 上会出错
- 在 Linux 上创建的文件名包含 `?` 或 `*`，Windows 上不认

### 6.3 文件权限

| 系统 | 权限机制 | 特点 |
|------|---------|------|
| Windows | NTFS 权限 | 比较复杂，用户组、权限继承 |
| Mac | Unix 权限 | 和 Linux 类似，也有 ACL |
| Linux | Unix 权限（rwx） | 读、写、执行，所有者、组、其他用户 |

**常见问题**：
- U盘从 Mac 拷到 Windows，文件变成"只读"
- Linux 服务器上文件权限不对，网站访问不了
- Mac 上下载的文件提示"来自身份不明的开发者"

## 七、跨平台兼容建议

### 7.1 普通用户建议

| 场景 | 建议 |
|------|------|
| **U盘/移动硬盘** | 格式化为 exFAT，Windows 和 Mac 都能用 |
| **文本文件** | 统一保存为 UTF-8 编码，避免乱码 |
| **文档分享** | 重要文件发 PDF，确保格式一致 |
| **图片分享** | JPG/PNG 通用，避免用系统专属格式 |
| **文件名** | 不用特殊字符、不用中文标点、空格尽量少用 |
| **压缩包** | 用 ZIP 格式，所有系统都能打开 |

### 7.2 程序员 / 开发者建议

1. **代码文件统一 UTF-8 + LF 换行**
2. **路径用正斜杠 `/`** 或用语言自带的路径处理函数
3. **文件名全小写 + 下划线**，避免大小写问题
4. **换行符用 `.editorconfig` 统一配置**
5. **Git 设置 `core.autocrlf`**，团队统一标准
6. **配置文件用 YAML/JSON/INI** 等跨平台格式
7. **尽量用相对路径**，不要写死绝对路径
8. **测试时在多系统上都测一遍**

### 7.3 团队协作建议

1. 制定统一的编码和换行符规范
2. 代码仓库设置 `.gitattributes` 文件
3. 新员工入职时配置好开发环境
4. 文档和设计稿统一用跨平台格式交付
5. 重要文件用版本控制工具管理，不要直接传来传去

---

## 💡 小结

1. **换行符**：Windows 用 CRLF，Mac/Linux 用 LF，文本文件跨平台时容易出问题
2. **编码**：Windows 老版本用 GBK，Mac/Linux 用 UTF-8，乱码的根源就是编码不统一
3. **路径分隔符**：Windows 用 `\`，Mac/Linux 用 `/`，编程时注意不要写死
4. **可执行文件**：各系统格式完全不同，`.exe` 不能在 Mac/Linux 上运行
5. **最佳实践**：统一用 UTF-8 编码、LF 换行、正斜杠路径、ZIP 压缩、exFAT 格式U盘
